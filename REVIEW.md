# Ревью API бронирования переговорных

Проект предоставляет API для создания, просмотра и отмены броней переговорных двух офисов. Авторизация — Bearer-токены Sanctum, хранение — PostgreSQL. Ожидаемая нагрузка: несколько сотрудников, включая одновременные запросы на одну комнату.

Ревью охватывает контроллер, маршруты, модели, миграции, фабрики, сидер, тесты и конфигурацию запуска.
Уровни: **critical** — нарушение безопасности и доступа к данным; **major** — нарушение правил бронирования или существенный пробел проверки; **minor** — локальная проблема производительности, диагностики или документации. Код приложения в рамках ревью не исправлялся.

## Обязательно исправить

### 1. critical — SQL-инъекция при проверке пересечений

**Где:** `app/Http/Controllers/BookingController.php:23–26`.

**Проблема:** `room_id`, `starts_at`, `ends_at` вставляются в SQL как текст. Например, строка `room_id = "1 OR 1=1 --"` меняет условие запроса ещё до попытки создания брони. Это позволяет вмешиваться в запрос от имени приложения; конкретный ущерб зависит от прав подключения к БД. Наличие `auth:sanctum` не защищает от такого ввода авторизованного пользователя.

**Исправление:** использовать Query Builder/Eloquent с параметрами, например `where('room_id', $roomId)`, а затем два условия пересечения и `exists()`. Сначала валидировать вход. Одна валидация без параметризации не заменяет исправление SQL.

**Если оставить:** пользователь сможет менять смысл запросов к общей базе; возможны утечки и отказ в обслуживании.

## Статус после исправлений

Замечания к `store` и `destroy` исправлены: Request, DTO, сервис и репозиторий; параметризованные запросы, проверка автора, валидация и UTC. Гонка защищена блокировкой комнаты в транзакции. Для пункта 14 первоначальный вывод скорректирован после воспроизведения тестом. По просьбе автора `index` и `today` возвращены к исходной реализации: замечания 10 и 12 остаются только в ревью, их исправление не входит в доработку. Тесты, проверявшие изменённое поведение `today`, удалены вместе с этой доработкой.

Автоматическое исправление ранее сохранённых неоднозначных дат не выполняется, чтобы не испортить данные. Ограничения миграции и контракт API описаны в README. Результаты текущих проверок приведены в конце документа; старые ограничения раздела первоначального ревью относятся к моменту его составления.

### 2. critical — Можно создавать брони от имени другого пользователя

**Где:** `app/Http/Controllers/BookingController.php:37`, `app/Models/Booking.php:11`.

**Проблема:** `Booking::create($request->all())` принимает клиентский `user_id`, который разрешён в `Fillable`. Анна может передать `user_id` Бориса: бронь будет записана ему и попадёт в его список. Внешний ключ проверяет существование пользователя, но не право действовать от его имени.

**Исправление:** брать автора только из `$request->user()`. Создавать бронь через отношение пользователя или явно формировать массив проверенных полей и отдельно назначать авторский ID; клиентский `user_id` игнорировать либо запрещать. Сам по себе `Fillable` не является проверкой прав.

**Если оставить:** авторство и любые будущие проверки владельца опираются на подделанные данные.

### 3. critical — Любой пользователь может удалить чужую бронь

**Где:** `app/Http/Controllers/BookingController.php:45–49`.

**Проблема:** `findOrFail($id)` ищет бронь среди всех записей. Борис может удалить бронь Анны, указав её ID: middleware проверяет только наличие авторизации.

**Исправление:** искать бронь через `$request->user()->bookings()->findOrFail($id)` либо проверять владельца в Policy перед удалением. Для этого проекта первый вариант достаточен; чужая бронь возвращает 404, либо при явной проверке — 403.

**Если оставить:** сотрудник может отменять встречи других сотрудников.

### 4. major — Нет проверки структуры ввода и предсказуемых ошибок 422

**Где:** `app/Http/Controllers/BookingController.php:21–37`.

**Проблема:** отсутствующие даты, массив вместо строки, несуществующая комната или отсутствующий `title` доходят до SQL/Carbon/INSERT. Вместо понятных ошибок по полям клиент получает исключения и 500. Свободный парсер также не обеспечивает требование ISO 8601 с явным смещением. Конфликт возвращается как 409, тогда как README требует ошибки валидации 422.

**Исправление:** подключить законченную валидацию до обращений к SQL: обязательность и типы полей, существование комнаты, строковый `title` в пределах размера столбца, корректные даты ISO 8601 с `Z` или смещением. Использовать только проверенные значения и единый формат ошибок по полям. Для задания возвращать 422 и при занятом слоте; 409 допустим как самостоятельный API-контракт, если требования явно изменят.

**Если оставить:** обычные ошибки клиента выглядят как поломка сервера и могут маскировать остальные нарушения правил.

### 5. major — Не проверяются длительность, порядок границ и шаг времени

**Где:** `app/Http/Controllers/BookingController.php:32–37`.

**Проблема:** в пустой комнате принимаются интервалы 10:00–10:05, 10:00–15:00, 10:00–09:00, 10:00–10:00 и 10:07–10:37. Секунды тоже не проверяются. Миграция не содержит ограничения `ends_at > starts_at`.

**Исправление:** сравнивать моменты времени, требовать положительную длительность 15–240 минут включительно. Обе границы проверять на сетку четвертей часа в местном времени офиса, с нулевыми секундами и дробной частью. Добавить базовый CHECK порядка границ как защиту данных от записи в обход HTTP.

**Если оставить:** сохраняются невозможные и запрещённые брони; дальнейшая проверка пересечений работает с некорректными интервалами.

### 6. major — Рабочее время проверяется по смещению клиента и только для начала

**Где:** `app/Http/Controllers/BookingController.php:32–34`, отношение `Room::office()`.

**Проблема:** `Carbon::parse(...)->hour` берёт час из присланной строки, а часовой пояс офиса не используется. Для Москвы `2026-11-10T06:00:00Z` — разрешённые 09:00, но запрос отвергается. Для Новосибирска начало в `19:00+03:00` означает 23:00 в офисе, но проходит проверку. Интервалы 19:00–21:00 и до следующего дня тоже проходят, поскольку конец не проверяется.

**Исправление:** получить `room.office.timezone`, перевести обе границы в этот пояс, требовать одну местную дату и полное попадание в 09:00–20:00. Конец ровно в 20:00 разрешён. Проверку длительности выполнять по абсолютному времени.

**Если оставить:** результат зависит от оформления запроса, а сотрудники бронируют комнаты после закрытия.

### 7. major — При сохранении и сравнении теряется смещение времени

**Где:** `app/Models/Booking.php:17–22`, `database/migrations/2026_10_29_000003_create_bookings_table.php:15–16`, `BookingController.php:23–26,37`.

**Проблема:** столбцы — `timestamp without time zone`, а явного перевода в UTC перед записью нет. Стандартный Eloquent `fromDateTime()` форматирует дату без сохранения смещения; PostgreSQL при сравнении с таким столбцом также игнорирует смещение литерала. Поэтому 10:00+03:00 и 14:00+07:00, обозначающие один момент, могут выглядеть как разные слоты. Обратный случай — одинаковые часы с разными смещениями считаются совпадением. При чтении потерянное смещение восстановить нельзя.

**Исправление:** до поиска пересечений и записи переводить обе границы в UTC и последовательно применять этот контракт во всех запросах. Для небольшого проекта можно сохранить текущие столбцы, храня в них исключительно UTC. Альтернатива — `timestampTz` с корректной сериализацией, но одна замена типа столбца не исправит потерю смещения в подготовке значений Eloquent. Существующие неоднозначные данные исправлять отдельно: слепой сдвиг всех строк небезопасен.

**Если оставить:** разрешаются фактические пересечения и отображается неверное время. Поведение сверено с [кодом Eloquent 13.39.0](https://raw.githubusercontent.com/laravel/framework/v13.39.0/src/Illuminate/Database/Eloquent/Concerns/HasAttributes.php) и [правилами PostgreSQL](https://www.postgresql.org/docs/17/datatype-datetime.html).

### 8. major — Соседние встречи ошибочно считаются пересекающимися

**Где:** `app/Http/Controllers/BookingController.php:25–26`.

**Проблема:** используются `<=` и `>=`. После брони 10:00–11:00 нельзя создать 11:00–12:00; симметрично блокируется встреча, заканчивающаяся в 10:00.

**Исправление:** представлять интервалы как полуоткрытые `[start, end)`. Пересечение существует при `existing.starts_at < newEnd AND existing.ends_at > newStart`. Сравнивать нормализованные моменты и проверять наличие через `exists()`.

**Если оставить:** разрешённые правилами слоты недоступны даже при последовательных запросах.

### 9. major — Проверка конфликта не защищает от одновременных запросов

**Где:** `app/Http/Controllers/BookingController.php:23–37`, миграция `bookings`.

**Проблема:** два запроса успевают прочитать отсутствие конфликта до первого INSERT и оба создают бронь. Ограничения пересечений в БД нет. Это бонусная часть задания, но реальная ошибка при нескольких клиентах.

**Исправление:** минимальный вариант — транзакция с `lockForUpdate()` на существующей строке комнаты, затем проверка пересечений и создание. Все пути создания должны соблюдать этот порядок. Блокировки только найденных броней недостаточно: при пустом расписании блокировать нечего. Простая транзакция без общей блокировки также не решает гонку. Более сильная защита — PostgreSQL EXCLUDE по комнате и диапазону `[)`, с `btree_gist`; выбирать `tsrange` или `tstzrange` в соответствии с типом столбцов и преобразовывать конфликт ограничения в понятный ответ.

**Если оставить:** двойные брони возможны при совершенно корректном вводе. По условиям README решение допустимо описать вместо реализации.

### 10. major — `today` определяет день в UTC и выдаёт время без пояса

**Где:** `app/Http/Controllers/BookingController.php:52–60`, `config/app.php` (`timezone = UTC`).

**Проблема:** `today()` использует пояс приложения, а не офиса; `whereDate` отбрасывает время. В 01:00 10 ноября в Новосибирске ещё 9 ноября UTC: метод выбирает другой день. После нормализации хранения в UTC ошибка сохранится без исправления границ выборки. Строка `time` склеивает даты без явного пояса, поэтому клиенту сложно правильно интерпретировать их.

**Исправление:** получить начало местного дня и начало следующего дня для офиса, перевести границы в UTC и выбирать по `starts_at >= from AND starts_at < to`. Возвращать отдельные `starts_at`/`ends_at` в ISO 8601 с явным поясом, а оформление оставить клиенту. Добавить сортировку по началу, если API должен выдавать расписание по порядку.

**Если оставить:** утром показываются брони другого дня. По заданию этот метод достаточно разобрать в ревью.

## Следует исправить

### 11. major — Тесты не проверяют создание и отмену броней

**Где:** `tests/Feature/BookingIndexTest.php:15–32`.

**Проблема:** два существующих теста проверяют только выдачу своих броней и отсутствие авторизации на GET. Они не обнаруживают ни одно из нарушений `store`/`destroy`, хотя README прямо требует feature-тесты на правила бронирования.

**Исправление:** добавить проверки успешного создания с автором из токена; попытки подменить автора; удаления своей/чужой/несуществующей брони; отсутствия токена на записи; обязательных полей и неверных типов; всех форм пересечения и соседних встреч; независимости комнат; длительности 15 и 240 минут и выхода за границы; шага, секунд и дробей; 09:00 и конца в 20:00; перехода даты; двух офисов и эквивалентных дат с разными смещениями. Проверять не только статус, но и состояние БД. Не добавлять запрет прошлых дат: его нет в задании. При реализации бонуса нужен отдельный тест с двумя подключениями/процессами.

**Если оставить:** исправления и дальнейшие изменения невозможно надёжно проверить существующим набором.

### 12. minor — `today` делает отдельный запрос автора для каждой брони

**Где:** `app/Http/Controllers/BookingController.php:54–59`.

**Проблема:** обращение `$b->user->name` лениво загружает отношение в цикле. Для N броней выполняются запрос расписания и ещё N запросов пользователей, даже когда автор повторяется.

**Исправление:** загрузить авторов заранее через `with('user')`. Для текущего небольшого демо дополнительная архитектура и кеш не нужны.

**Если оставить:** время ответа и нагрузка на БД растут с числом броней за день.

### 13. minor — ID брони добавляется в контекст другого канала логирования

**Где:** `app/Http/Controllers/BookingController.php:39–40`, `config/logging.php`.

**Проблема:** при штатном `LOG_CHANNEL=stack` вызов `Log::withContext()` меняет контекст канала по умолчанию. Следующая запись идёт в отдельный `bookings`, поэтому `Booking created` не получает ожидаемый `booking_id`.

**Исправление:** передать контекст прямо в запись: `Log::channel('bookings')->info('Booking created', ['booking_id' => $booking->id]);`. Общий контекст на все каналы для одной записи не нужен.

**Если оставить:** журнал не позволяет связать событие с бронью. Разделение контекстов подтверждается [LogManager 13.39.0](https://raw.githubusercontent.com/laravel/framework/v13.39.0/src/Illuminate/Log/LogManager.php).

### 14. minor — API возвращает 500 вместо 401 без Accept

**Где:** `README.md:96`, `bootstrap/app.php:18–21`.

**Проблема:** первоначальный вывод ревью о достаточности `shouldRenderJsonWhen()` оказался неверным. При проверке реальным feature-тестом middleware авторизации до обработки исключения вызывает отсутствующий маршрут `login`, что приводит к 500. README описывал исходное поведение правильно.

**Исправление:** настроить `redirectGuestsTo()` так, чтобы API не строил URL страницы входа; JSON-обработку исключений оставить включённой. Обновить README после исправления и проверить обычный запрос без Accept.

**Если оставить:** неавторизованный клиент получает серверную ошибку вместо 401. Ошибка исходного ревью исправлена по результатам теста.

## Подозрительно, но само по себе не ошибка

- `index()` ограничен `user_id` из авторизованного пользователя. Чужие брони этим методом не выдаются; это уже проверяет feature-тест.
- `orderByRaw('starts_at DESC')` в `index()` содержит константу, без пользовательского ввода. Здесь нет SQL-инъекции. `orderByDesc('starts_at')` проще, но это не критическое исправление. Для стабильных страниц при одинаковом `starts_at` можно добавить вторичную сортировку по ID.
- Атрибуты `#[Fillable]` и `#[Hidden]` соответствуют используемому Laravel 13; их нельзя считать ошибкой только потому, что раньше чаще применялись свойства моделей.
- `BookingFactory` использует `$startsAt->copy()->addHour()`: исходная дата начала при вычислении конца не меняется.
- Общий `auth:sanctum` на маршрутах действительно есть. Проблема удаления — в отсутствии проверки владельца, а не в открытом маршруте.
- Просмотр имён авторов в расписании комнаты сам по себе не нарушение требований: README не вводит разграничение доступа по офисам.
- Отсутствие запрета прошлых дат, выходных и далёкого будущего соответствует заданию: других ограничений на даты нет.
- `anna-token` и `boris-token` явно обозначены как демонстрационные, в БД сохраняются их хеши. Для локального задания это не новая критическая находка; такие токены и `APP_DEBUG=true` нельзя переносить в публичную рабочую среду.
- `migrate:fresh --seed` допустим для первоначального заполнения демо. Он удаляет существующие таблицы и данные, поэтому не является командой обычного обновления работающей базы.
